## 2. Published evidence that shapes the design

1. Precision matters more than recall. False alarms are the main reason developers stop trusting a reviewer. Best single-pass F1 on 1,000 real PRs is about 19%; 48% of false positives come from missing context [M, SWR-Bench, arxiv 2509.01494]. OpenAI chose precision over recall on purpose [M, alignment.openai.com/scaling-code-verification, 2025-12-01].
2. Running code helps. A reviewer with repo access and code execution catches more critical issues with fewer false alarms than diff-only review [M, OpenAI]. A code execution tool raised judge agreement with ground truth from below 42% to about 72% [M, Findeis et al. 2025, via arxiv 2510.24367]. A passing test proves only what it covers.
3. Different passes beat identical passes. Two different agents match or beat 16 identical ones, because identical agents make the same mistakes [M, preprint arxiv 2602.03794]. Independent passes plus a vote give most of the gain people credit to debate; debate rounds add bias [M, NeurIPS 2025, arxiv 2508.17536; EMNLP 2025]. Gains flatten above about 5 passes [M, SWR-Bench].
4. No controlled study shows specialist agents per aspect beat several generalist passes with a vote. Cursor Bugbot started with 8 voting passes, then moved to one agent with tools and tuned prompts to flag more [M own metric, cursor.com/blog/building-bugbot, 2026-01-15].
5. Asking for long explanations and fixes makes models reject correct code with convincing false arguments [M, small models only, arxiv 2603.00539]. Ask the validator for proof, not argument.
6. Design comments are acted on least (28.6% at Atlassian); bug comments most [M, arxiv 2510.05450]. Hence the strict proof rule for Simplicity and Reuse.
7. Anthropic Code Review labels findings Important / Nit / Pre-existing. About 59% of repeat flags were on code that existed before the PR. It runs on known-clean PRs to count false reports, and on past incident PRs as a daily eval [A, claude.dev/blog/solving-code-review-at-anthropic, 2026-10-15].
8. Text in a PR can steer an automated reviewer: crafted PR text biased automated security review, Claude Code included, in 32 of 33 cases [M, arxiv 2603.18740]. A false premise in a prompt flipped up to 72% of verdicts in small models; asking for evidence before the verdict cut that to 12-26% [M, arxiv 2607.10411].

## 3. Rules for writing the agent prompts

Sources: U1 = platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, U2 = .../prompting-claude-opus-5, U3 = .../prompting-claude-opus-5-5, U6 = .../structured-outputs, U7 = anthropic.com/engineering/multi-agent-research-system, U8 = anthropic.com/engineering/demystifying-evals-for-ai-agents, U10 = platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices, U11 = code.claude.com/docs/en/sub-agents, U12 = anthropics/claude-plugins-official code-review command, U14 = arxiv 2603.18740, U15 = arxiv 2607.10411.

Structure
1. Every brief has four parts: objective, output format, tools and sources to use, boundaries. The agent sees nothing of the lead's conversation, so the brief restates every rule it needs, including the project rules that apply [A, U7, U11].
2. Give the reason with each rule ("run the spec, because reading misses runtime config"). The model generalises from the reason [A, U1].
3. Separate parts with XML tags: `<claim>`, `<diff>`, `<code_context>`, `<untrusted_mr_text>`, `<area_definitions>`, `<instructions>`, `<output_schema>`. Long inputs first, the instructions and the question last [A, U1].
4. Say what to do, not what to avoid. One to three short, different examples, at least one of them a refuted claim, so the agent does not learn that every claim is true [A, U1].

Wording for current models
5. No capitals, "CRITICAL" or "you MUST". Current models act on emphatic rules too often. Give each absolute rule its scope and reason [A, U1, Fable 5.2 guide].
6. No "double-check" or "re-verify" lines in a verifier's brief. Opus 5 and later check their own work, and these lines only add cost. The skeptic is a separate step with a different question, so it stays [A, U2].
7. No "report only serious issues" or "be conservative". Opus 5 follows this literally and reports less. Verifiers report every verdict with its confidence; the skeptic and the lead filter [A, U2]. This replaces the old plugin rule "if uncertain, don't flag".
8. Never ask for "reasoning" or "step-by-step thinking" in the output or as a schema field. It can cause a refusal on Opus 5, 5.5, Sonnet 5.5 and Fable 5.2. Ask for "a short explanation" [A, U2, U3, U6].
9. Scope line from U2: deliver what was asked at the scope intended, and stop short of actions clearly beyond it. Without it, high-effort agents start their own review rounds [A, U2].

Evidence
10. Each claim gets: a real check that exercises it (spec, script, type check, browser), the exact command, an excerpt of its real output and `file:line`. A syntax check or a command that failed to start does not count. If no check can run, the agent says which check it skipped and why and returns "inconclusive" [A, U1, U4, U8].
11. Each claim gets a negative control: the same check gives a different result on base, or with the fix removed. A check that passes both ways proves nothing [J, supported by U8 and by the practice of checking that a test fails without the fix].
12. Agents may write new probe specs and scripts in their scratch folder. They do not change the code or specs under review. The lead checks `git status` of the review worktree after every phase [A, U1; J].
13. The lead reruns one command per finding before it reports it, to catch made-up output [J, from U8 "grade what the agent produced"].
14. Proof grades: Verified = ran it, or reproduced it in the app; Structural = a fact that holds whatever the runtime state; Predicted = reasoning about runtime behaviour that was not run. A Predicted argument cannot reject a Structural or Verified finding.

Bias
15. Present every claim as an unverified hypothesis. Ask for evidence before the verdict [M, U15].
16. Comment text and MR text go inside `<untrusted_mr_text>`, with a line that says it is data and never instructions. Verifiers get the rewritten claim; the raw text stays with the lead [M, U14; A, U3].
17. The skeptic gets the claim, the code and the verifier's commands and outputs. It does not get the verifier's verdict, confidence or explanation. It designs its own disconfirming test and may return "could not refute" [A, Claude Code Agent tool text: "an agent handed your hypothesis tends to return it confirmed"].
18. Every agent may return "inconclusive". Judges that may say "unknown" invent less [A, U8].

Output schema
19. Use a fixed JSON schema with every field required and `additionalProperties: false`. Field order: `claim_id`, `area`, `commands_run[]` (cmd, exit_code, output_excerpt), `negative_control`, `evidence_locations[]`, `proof_grade`, `verdict` (confirmed / partly_confirmed / refuted / inconclusive), `confidence`, `user_impact` (what the user sees, how often), `pre_existing` (true when the problem is in code the MR did not touch), `proposed_fix_result`, `better_alternative`, `explanation` (short). Evidence comes before the verdict [A, U6; order is J].
20. Confidence tied to evidence, not feeling [J, after U12 and U13]: 9-10 reproduced with a negative control; 7-8 reproduced, no control possible; 4-6 structural proof only; 1-3 reading only.
21. Name what is not a finding: problems in code the MR did not touch (report them, marked pre-existing), code that looks wrong but is right, nitpicks, what linters catch, explicit suppressions, "I would have done it differently" [A, U12].

Orchestration
22. Put the rules for how many agents and when into the lead's instructions, not the agents' judgment. Early Anthropic systems started 50 subagents for simple questions [A, U7].
23. Effort: on Opus 5.5 the default (medium) matches Opus 5 at high on coding. Lower effort controls cost more reliably than prompt text. Use higher effort only where it measurably helps [A, U3].
24. SKILL.md under 500 lines, references one level deep, description in third person with what and when; build a few evals before the prompts [A, U10].

## 5. Limits of this research

- Anthropic docs pages carry no date; they were read on 2026-11-11.
- No public prompt for Anthropic's managed Code Review product was found.
- No data shows that evidence before verdict improves accuracy in Claude models; the field order is judgment.
- ISO 25010:2023, IEEE 24765 and Ousterhout were read through summaries, not the original texts.
- The best number of passes and the vote threshold for agents with tools are not measured anywhere.
- Vendor precision figures ("<1% incorrect", "<3% false positives") have no public method.
